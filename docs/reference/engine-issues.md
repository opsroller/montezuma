# Engine issues we work around

*Reference. Godot behaviour that the project had to work around, with the
engine version it was seen on, what we did and what would let us undo it.
Why the engine version is what it is: [About the engine version](../explanation/about-the-engine-version.md).*

| Seen | Godot | What happens | What we do | Undo when |
|---|---|---|---|---|
| 2026-10-23, Mac mini M4, Metal | 4.8 beta 1 | The Forward Mobile renderer generates a scene shader for a `BaseMaterial3D` with `subsurf_scatter_transmittance_enabled` that it cannot compile: the generated fragment calls `light_compute` with the transmittance arguments, which the Mobile variant does not have, so the compile fails with `'light_compute' : no matching overloaded function found` and `missing #endif`, and the renderer then aborts on an empty pipeline list (`Index p_index = 25 is out of bounds (size() = 0)`). Subsurface scattering itself is only warned about and stripped, as documented. | The temple's gem materials keep subsurface scattering and leave transmittance out: `gen_theme_scenes.py` writes transmittance only when a theme's `subsurface` block names a `transmittance` colour, and `tools/assets/themes/temple.json` does not ([Board themes](board-themes.md#generators), the `materials` table). | A Godot release strips transmittance on Mobile like it strips subsurface scattering. Not reported upstream from this project; the owner decides what goes out under the project's account. |
| 2026-10-23, Mac mini M4 | 4.7.2, 4.8 beta 1 | With `xr/openxr/enabled=true` and no OpenXR runtime installed, start-up shows a modal "OpenXR was requested but failed to start" alert and waits for a click, so an unattended run (benchmark, CI-style check) hangs in `NSAlert runModal`. | The project enables OpenXR by choice; `xr/openxr/startup_alert=false` in `project.godot` turns the alert into the log line, and headless runs (CI, the smoke test, the how-to) pass `--xr-mode off` so the log stays clean. | Never: the alert is for players, the log line is for us. |
| 2026-10-24, Mac mini M4 | 4.8 beta 1 | With `rendering/driver/threads/thread_model=2` (separate render thread), a node that loads a scene and its assets with `ResourceLoader.load_threaded_request` never sees them finish (headless and with a window alike; the main thread idles in its loop), while the same code loads in 0.2 s with the single-thread model. | The benchmark loads the board directly, as before; the `ScenePreloader` and primer scene tried on 23 October were taken out again. | A Godot release where threaded loading completes under the separate render thread, or a different model in the project. |
| 2026-10-24, GitHub macOS runner | 4.8 beta 1 | With `rendering/driver/threads/thread_model=2` (the separate render thread, which Godot marks experimental) the exported game logs `This function (finalize) can only be called from the render thread` and two leaked objects at exit. | The smoke test allows that line by exact text (`tools/release/smoke-test.cmake`); the game runs and quits normally. Work package 64. | A Godot release that finalizes the rendering device on the right thread under that model, or another model in the project. |
| 2026-10-24, GitHub Linux runner | 4.8 beta 1 | With `display/window/hdr/request_hdr_output=true` Godot turns HDR 2D on for every driver, and the Movie Maker frame capture on OpenGL then logs `Condition "format != FORMAT_RGB8 && ..." is true` from `Image::linear_to_srgb` for every frame. A per-renderer override is not possible: feature-tag overrides resolve before the rendering method is chosen. | The smoke test allows that line by exact text; the captured frames are written. Work package 64. | A Godot release whose OpenGL capture converts HDR 2D frames, or HDR output off in the project. |
| 2026-10-24, GitHub macOS runner (Apple Paravirtual device, Apple5) | 4.8 beta 1 | The device reports 32-bit image atomics, so volumetric fog takes the image path in `Fog::VolumetricFog::init` and creates its density map as an `R32_UINT` atomic storage image (a device without that feature gets a storage buffer instead), which this device then refuses: `Format 'R32_Uint' does not support usage as atomic storage image`, null textures, then a segfault in the first frame with volumetric fog on. Real Apple GPUs (M4 here) run it. `main` passed only because the tier system switched volumetric fog off on that runner. | Open: work package 65. The packaged-game smoke on macOS fails until the runner, the engine or the content changes. | A Godot release that checks the format's atomic support (or uses the storage-buffer path) on that device, or a runner with a real GPU. |
| 2026-10-20, Mac mini M4 | 4.7.2 | Godot's Metal driver returns no GPU timestamps, so `viewport_get_measured_render_time_gpu` is 0 and `--gpu-profile` prints zeros. | Measure GPU time on 4.8 beta 1, which reports it; on 4.7.2 use whole-frame time with vsync off ([Benchmark results](benchmark-results.md)). | 4.7.x backports the Metal timestamps. |
